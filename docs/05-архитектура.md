# 05. Архитектура

## Развёртывание

Веб-сервис на сервере, работает круглосуточно. Один VPS на старте.

```
┌─────────────────────────────────────────────────┐
│ VPS                                             │
│                                                 │
│  ┌───────────┐   ┌──────────┐   ┌────────────┐  │
│  │ Харвестер │   │ Воркеры  │   │ Веб (Next) │  │
│  │ Playwright│   │ этапов   │   │            │  │
│  └─────┬─────┘   └────┬─────┘   └──────┬─────┘  │
│        │              │                │        │
│        └──────┬───────┴────────────────┘        │
│               │                                 │
│        ┌──────▼──────┐    ┌─────────────┐       │
│        │ PostgreSQL  │    │ Файлы (диск │       │
│        │ + pg-boss   │    │ или MinIO)  │       │
│        └─────────────┘    └─────────────┘       │
└─────────────────────────────────────────────────┘
         │                    │
         ▼                    ▼
   zakup.sk.kz          Claude API
   old.goszakup.gov.kz  Telegram Bot API
```

Все процессы на одной машине. Разносить рано: поток лотов с одной площадки
невелик, а лишние движущиеся части на старте дороже, чем полезны.

## Харвестер — критический узел

**Почему обычный HTTP-клиент не подходит.** Прямой запрос к API портала
возвращает **418**: нужен подписанный заголовок `tor`, который ставит само
приложение. Ссылки на файлы — `javascript:;`, реальный URL вида
`eprocfilestorage/open-api/files/download/<uuid>` появляется только после
действия в интерфейсе. Значит, и обход, и скачивание идут **из одного живого
браузерного контекста**.

**Устройство:**
- один persistent context, переживающий перезапуски (профиль на диске)
- последовательный обход, **не параллельный** — портал начинает отдавать ошибки
  при частых запросах, это зафиксировано на практике
- пауза между запросами, настраиваемая; при первой же серии ошибок пауза
  удваивается автоматически
- перехват `XMLHttpRequest.prototype.open` для получения URL файлов
- смена hash требует `location.reload()` — SPA не перерисовывает попап сама
- `cin` в URL переживает перезагрузку, `cust` — нет; надёжный путь — заполнить
  форму и нажать «Найти»

**Health-check.** Если харвестер не завершил ни одного успешного обхода за N
часов — алерт в Telegram. Молчащий харвестер неотличим от «новых лотов нет», и
это самый опасный отказ в системе.

**Нагрузка на портал.** Обход должен быть щадящим: это чужая инфраструктура, и
слишком частые запросы уже приводили к ошибкам. Частота подбирается от
минимальной вверх, а не наоборот.

## Авторизация

На первой итерации — **без входа**. Практически все тендеры видны публично;
недоступен только протокол предварительного обсуждения.

Вход требует **ЭЦП и пароля**, поэтому автоматизировать его нельзя так же
просто, как логин с паролем. Когда протокол предварительного обсуждения
понадобится, вариантов два:

1. **Ручная сессия.** Человек один раз входит через браузер на сервере
   (VNC/удалённый рабочий стол), сессия сохраняется в persistent context,
   харвестер её переиспользует до истечения. При истечении — уведомление
   «нужно переподключиться».
2. **Подпись на стороне.** Отдельный компонент с доступом к ключу. Сложнее и
   требует отдельного решения по хранению ключа.

Первый вариант проще и достаточен. **Ключ ЭЦП на сервер не кладётся** ни в
каком виде — в модели угроз это неприемлемо.

## Старый портал

`old.goszakup.gov.kz` устроен проще: внутри страницы того же домена работают
обычный `fetch` и `DOMParser`, браузерный контекст не обязателен. Но лимит по
частоте там жёстче: портал начинает отдавать ошибки быстро. Поэтому запросы
к нему идут через ту же очередь с ограничением скорости, а при отказе система
**отвечает по уже собранному и помечает результат как неполный** — молчаливой
потери данных быть не должно.

## Анализ

Каждый блок этапа 4 — отдельный вызов со своей JSON-схемой и своим промптом.
Плюсы против одного большого промпта:
- сбой одного блока не роняет весь разбор
- версия промпта и стоимость видны по блокам
- дорогая модель применяется только там, где нужна

Распределение по моделям: тип договора (4.1), экономика (4.6) и запас по цене
(4.7) — там, где ошибка меняет вывод по существу, — на старшей модели; остальные
блоки на быстрой. Конкретные идентификаторы моделей — в конфиге, не в коде.

**Контекст.** Комплект документации не влезает в одно окно целиком. Каждому
блоку подаются только релевантные секции, выбранные по `section_path` и
полнотекстовому поиску. Разбиение по секциям на этапе 2 существует ровно для
этого.

**Стоимость.** Меряется по каждому прогону (`analysis.cost`) и выводится в
интерфейс агрегатом за период. Без этой цифры невозможно осмысленно настраивать
пороги триажа: экономика продукта — это отношение стоимости анализа к ценности
найденных лотов.

## Площадки

`platform` заложена в схему с первого дня, а специфика портала изолирована в
адаптере:

```
PlatformAdapter
  listLots(filter)      → сырые карточки
  fetchLotDetail(id)    → детали
  listDocuments(lotId)  → метаданные файлов
  downloadDocument(ref) → содержимое
  contractHistory(...)  → реестр договоров
  checkSupplier(bin)    → статус в реестрах
```

Этапы 2–9 от площадки не зависят вообще. Добавление площадки = новый адаптер +
маппинг полей, без правки конвейера. Это единственная уступка будущему, которую
стоит делать сейчас; всё остальное — по факту.

## Что не делаем сейчас

- Kubernetes, микросервисы, отдельные очереди на этап
- Свой поисковый движок — хватит полнотекстового поиска Postgres
- Мобильное приложение — Telegram закрывает мобильный сценарий
- Многопользовательский доступ в интерфейсе
