# 10. Слой сбора: как программа цепляет новый тендер

Как в реальном времени поймать только что вышедший тендер, вытащить по нему всё
и отдать обработчику.

---

## 1. Что такое один тендер

Три уровня вложенности, и всё:

```
ЗАКУПКА                          ← одна карточка на портале, свой номер
  заголовок
  заказчик
  тип (открытый тендер / ЗЦП)
  статус (предобсуждение / опубликовано)
  даты: опубликовано · приём с · приём до
  общая сумма
  │
  ├── ЛОТ 1    название · сумма · место · срок
  ├── ЛОТ 2    название · сумма · место · срок
  │
  └── ДОКУМЕНТЫ
        общие по закупке    → тендерная документация, проект договора
        по лоту             → техспецификация, приложения
```

Это ровно та карточка, что на макете. Структура данных повторяет структуру
экрана намеренно.

В базе — три таблицы: `purchase` → `lot` → `document`, плюс связка «файл ↔ лот»
(файл может относиться ко всей закупке или к конкретному лоту, и один и тот же
файл встречается в разных закупках). Поля — в [04-данные.md](04-данные.md).

### Обложка и документы — разные по природе

| | Обложка | Документы |
|---|---|---|
| Откуда | строка списка и карточка закупки | PDF и DOCX |
| Что там | заголовок, тип, цена, лоты, даты, заказчик | квалтребования, оплата, демпинг, штрафы, объёмы |
| Объём | ~15 полей | десятки страниц |
| Как быстро получаем | секунды | минуты |

Поэтому обложка попадает в ленту сразу, а документы разбираются следом. Это и
есть два такта уведомления.

## 2. Как это устроено

```
   ┌─────────────┐
   │    ДОЗОР    │  раз в минуту открывает первую страницу списка
   │             │  (сортировка: сначала новые)
   └──────┬──────┘
          │  сверяет верхние строки с базой
          │  всё знакомо → выход, работы нет
          │  новая строка → задача «собрать закупку 1247669»
          ▼
   ┌─────────────┐
   │   СБОРЩИК   │  открывает карточку закупки
   │             │  забирает поля и ссылки на файлы
   │             │  качает файлы
   └──────┬──────┘
          ▼
   ┌─────────────┐
   │    БАЗА     │  закупка + лоты + файлы на диске
   └──────┬──────┘
          │  задача «разобрать лот 4514471»
          ▼
   ┌─────────────┐
   │ ОБРАБОТЧИК  │  текст → фрагменты → модель → карточка
   └─────────────┘
```

**Дозор.** Один запрос в минуту: 20 верхних строк списка, отсортированного по
дате публикации. Все номера знакомы — выход. Появился незнакомый — ставит
задачу. Если за минуту вышло больше 20 лотов, берёт вторую страницу; на практике
не случается.

**Сборщик.** По номеру закупки открывает карточку
(`#/ext(popup:item/1247669/advert)`), забирает поля и перечень файлов, качает их,
пишет в базу.

**База.** Поля — колонками, по ним фильтруется лента. Файлы — на диске, имя файла
= sha256 его содержимого.

**Обработчик.** Этапы 2–7 из [02-конвейер.md](02-конвейер.md).

Плюс подстраховка: раз в сутки в тихий час проход по окну «последние 72 часа»
целиком, мимо дозора. Ловит то, что проскочило во время простоя. Количество
находок прямо показывает, насколько дозору можно доверять.

## 3. Как именно данные добываются с портала

Здесь единственная по-настоящему нерешённая техническая задача проекта.

### Что известно

**Портал не отдаёт данные простому HTTP-запросу.** Прямой `fetch` к API возвращает
**418**: нужен подписанный заголовок `tor`, который ставит само приложение.
Ссылки на файлы в интерфейсе висят на `javascript:;` — настоящий URL появляется
только после действия в интерфейсе.

**Но файлы скачиваются обычным HTTP.** Ссылка вида
`zakup.sk.kz/eprocfilestorage/open-api/files/download/<uuid>` читается простым
запросом без подписи. Косвенное, но убедительное подтверждение: такие ссылки
**проиндексированы поисковиками** — значит, их забирал краулер, без всякого
браузера.

Отсюда главное следствие: **браузер нужен, чтобы узнать ссылку, а не чтобы
скачать файл.**

**Официального API у zakup.sk.kz не обнаружено.** Три поисковых захода не нашли
ни раздела для разработчиков, ни документации, ни выдачи ключей. Зато нашёлся
сторонний платный скрапер на Apify (`alex-dev-kz/zakup-sk-scraper`), собирающий
заголовки, бюджеты и ссылки с поддержкой пагинации. Существование такого продукта
косвенно говорит, что официального пути нет — иначе он был бы не нужен.

**У `old.goszakup.gov.kz` официальный API есть.** Унифицированные сервисы
`ows.goszakup.gov.kz/v2`, документация на `goszakup.gov.kz/ru/developer/ows_v2`,
авторизация персональным токеном по схеме Bearer, токен выдаётся по письму в
Минфин РК сроком на год. Для второй площадки это меняет план целиком: там не
нужен ни браузер, ни парсер. **Запросить токен стоит заранее** — выдача идёт по
письму и занимает время.

### Четыре варианта

| | Что это | Цена разработки | Оценка |
|---|---|---|---|
| **A** | Официальный API zakup.sk.kz | почти ноль | признаков существования нет |
| **B** | Свой HTTP-клиент, воспроизводящий `tor` | день-два реверса | возможен, хрупок |
| **C** | **Гибрид: браузер добывает ссылки, HTTP качает** | несколько часов | **выбран** |
| **D** | Всё через браузер | — | запасной |

### Почему выбран C

```
БРАУЗЕР  (один, живёт постоянно)
  ├─ раз в минуту: первая страница списка       ← дозор
  ├─ на новый лот: карточка закупки             ← поля + ссылки на файлы
  └─ отдаёт наружу актуальные заголовки и куки

HTTP-КЛИЕНТ  (обычный, параллельный)
  └─ качает файлы по ссылкам                    ← весь объём здесь
```

**Не требует реверс-инжиниринга.** Подпись ставит сам браузер, мы её просто
переиспользуем. Поменяют алгоритм подписи — браузер пересчитает сам, наш код не
заметит.

**Даёт скорость там, где объём.** Объём — это файлы, порядка 15 МБ на лот, и они
уже доказанно качаются обычным HTTP параллельно. Браузеру остаётся страница
списка раз в минуту и карточка на новый лот: единицы запросов, где скорость
не важна.

**Деградирует, а не ломается.** Если подпись окажется непереносимой за пределы
браузера, тот же код ходит через браузер — это вариант D. Теряется
производительность, не работоспособность.

**Улучшается без переделки.** Если выяснится, что `tor` считается детерминированно,
это вариант B — меняется одна функция внутри gateway.

То есть C — не компромисс между B и D, а точка старта, из которой видны обе двери.

### Portal Gateway

Браузер — единственный, кто умеет разговаривать с порталом, он один, он падает и
не параллелится. Поэтому он не размазан по воркерам, а спрятан за отдельный
процесс с узким контрактом:

```
GET /lots?status=&page=       → строки списка
GET /purchase/<no>            → поля закупки и ссылки на файлы
GET /document/<uuid>          → байты файла (обычный HTTP, мимо браузера)
GET /health                   → состояние, длина очереди, текущая пауза
```

Внутри: одна очередь, конкурентность 1, пауза между запросами, удвоение паузы при
серии ошибок, восстановление контекста из профиля на диске.

Смысл границы — в том, что **вопрос «браузер или HTTP» остаётся деталью
реализации**. Сегодня внутри C, завтра B, для второй площадки — официальный API.
Снаружи не меняется ничего. Это единственная уступка будущему, которая здесь
оправдана.

### Что проверить, в этом порядке

Три опыта, каждый на 15–20 минут, на машине с доступом к порталу.

**Опыт 1. Качается ли файл без браузера.** Взять публично проиндексированную
ссылку и дёрнуть её голым curl:

```bash
curl -sS -o t.pdf -w '%{http_code} %{size_download}\n' \
  https://zakup.sk.kz/eprocfilestorage/open-api/files/download/fdd4e90d-1847-4df1-91a0-ee77371c7ccc-2021-mdb
```

200 и осмысленный размер → главная часть варианта C подтверждена.

**Опыт 2. Переживает ли подпись выход из браузера.** На странице списка в
DevTools найти запрос к API, «Copy as cURL», вставить в терминал. Работает →
заголовки переиспользуемы, C подтверждён целиком. Заодно выяснить, через сколько
минут перестаёт работать — это срок жизни подписи и частота её обновления.

**Опыт 3. Откуда берётся `tor`.** Поиск по строке `tor` в исходниках бандла SPA
в DevTools. Видно, что значение вычисляется функцией → открыт вариант B.

**Опыт 0, перед всеми.** Пройти по самому порталу: нет ли раздела для
разработчиков, открытых данных или выдачи ключа. Поиск ничего не нашёл, но
отсутствие в поиске — не доказательство.

Отдельно: проверить правила пользования порталом на предмет ограничений по
автоматическому сбору (открытый вопрос №8). Данные публичные и мы участник этих
закупок, но частоту и подход лучше согласовать с правилами до запуска, а не после.

## 4. Что где хранится

**Поля закупки и лотов** — колонками в Postgres. По ним фильтруется и сортируется
лента, поэтому они должны быть индексируемыми. Всё остальное — рядом в `jsonb`.

**Файлы** — на диске, путь выводится из sha256 содержимого:

```
storage/ab/cd/abcdef0123…4567.pdf
```

Это решает сразу несколько вещей бесплатно: нет коллизий имён (`Приложение
№1.pdf` встречается в каждой второй закупке), нет проблем с кириллицей в путях,
переезд на S3 — смена префикса. И главное: типовая документация одного заказчика
повторяется из закупки в закупку, совпадение по хешу означает, что файл **не
качается и не разбирается второй раз**.

**Текст и нарезанные фрагменты** — в базе, бессрочно. Они лёгкие.

**Сырой ответ портала** — тоже в базу, до всякого разбора. Не ради красоты: если
через месяц выяснится, что мы неправильно распознали поле, мы перегоняем разбор
по сохранённому, а не идём на портал за тендером, которого там уже может не быть.

## 5. Три вещи, которые легко упустить

**Тот же тендер увидим ещё раз.** Дозор смотрит 20 строк, завтра те же строки
могут снова оказаться наверху. Уникальный ключ — номер закупки плюс номер лота:
повторная запись обновляет `last_seen_at` и никаких задач не создаёт. Иначе один
тендер разберётся десять раз и десять раз будет оплачен.

```sql
insert into lot (platform_id, purchase_external_no, external_no, ...)
values (...)
on conflict (platform_id, purchase_external_no, external_no) do update
   set last_seen_at = now(), ...
returning id, (xmax = 0) as is_new;
```

`xmax = 0` отличает вставку от обновления одним запросом — так сборщик узнаёт,
что лот действительно новый.

**Тендеры меняются.** Продлили срок, выложили изменения в документации,
предобсуждение перешло в «Опубликовано». Поэтому сверяется не только «есть или
нет», но и короткий отпечаток по сумме, срокам, статусу и списку файлов.
Отпечаток считается по этим полям, а не по сырому ответу — в сыром меняются
служебные метки, и каждый лот выглядел бы изменившимся постоянно.

**Задача и запись пишутся одной транзакцией.** pg-boss живёт в том же Postgres,
поэтому `boss.send(..., { db: t })` внутри той же транзакции, что и запись лота.
Иначе процесс, умерший между двумя действиями, оставляет либо лот без задачи
(молча не разобран), либо задачу без лота (вечные ретраи).

И сквозное правило: **алерт на отсутствие, а не на ошибку.** Сломанный парсер
молча отдаёт ноль строк и неотличим от «новых лотов нет». Нет новых лотов больше
трёх часов в рабочее время → сообщение в Telegram.

## 6. Бюджет задержки

| Шаг | Время |
|---|---|
| Дозор заметил | до 60 с |
| Карточка закупки | ~3 с |
| **Лот в ленте, такт 1 уведомления** | **≈ 1 минута** |
| Документы | ~10 с (параллельно, обычным HTTP) |
| Текст и фрагменты | ~30 с |
| Разбор L1 | ~40 с |
| **Такт 2 — выжимка** | **≈ 2 минуты** |

Минута до ленты упирается в интервал дозора, а не в портал: хотим быстрее —
уменьшаем интервал.

Числа — оценки. Замеры появятся после спайка Ш-0.
