# 10. Слой сбора: обнаружение, извлечение, хранение, передача

Этот документ отвечает на один вопрос инженерно: **как программа в реальном
времени цепляет только что вышедший тендер, вытаскивает по нему всё и отдаёт
обработчику, не теряя данные и не ломаясь, когда портал изменится.**

[02-конвейер.md](02-конвейер.md) описывает этапы 0–2 по смыслу. Здесь — устройство.

---

## Задача в технической постановке

Исходная формулировка («извлекать всю информацию, хранить оптимально,
обрабатывать») распадается на четыре независимых вопроса. Смешивать их нельзя —
у каждого свой правильный ответ, и неверный ответ на один портит остальные.

| # | Вопрос | Суть |
|---|---|---|
| **Q1** | **Обнаружение** | Источник без push-канала. Как узнать о новом лоте за секунды, не опрашивая портал слишком часто и не пропуская записи, пришедшие не по порядку |
| **Q2** | **Извлечение** | Что такое «вся информация», из каких трёх разных источников она берётся и как получить её в структурированном виде, а не выскребать из вёрстки |
| **Q3** | **Хранение** | Что считать источником правды, чтобы смена разметки на портале не уничтожила уже собранное, и чтобы один и тот же файл не хранился и не разбирался дважды |
| **Q4** | **Передача** | Какой контракт между сборщиком и обработчиком даёт гарантию «ни одна задача не потеряна и ни одна не выполнена дважды» |

Плюс сквозной вопрос **Q5 — наблюдаемость**: как отличить «новых лотов нет» от
«сбор сломался и молчит».

---

## Ограничение, из которого следует вся архитектура

Портал доступен **только из живого браузерного контекста**: прямой запрос к API
возвращает 418, нужен подписанный заголовок `tor`, который ставит само
приложение; ссылки на файлы — `javascript:;`, настоящий URL появляется только
после действия в интерфейсе.

Отсюда следствие, определяющее всё остальное: **браузер — дефицитный, хрупкий и
последовательный ресурс.** Он один, он может упасть, он не параллелится, и он
единственный, кто вообще умеет разговаривать с порталом.

Значит, браузер нельзя размазывать по воркерам. Он должен быть отдельным
процессом с узким интерфейсом.

## Решение Q2a. Portal Gateway — единственный, кто трогает портал

Отдельный процесс. Внутри — один persistent context Playwright. Наружу — HTTP/JSON.

```
GET /lots?status=&page=          → сырой ответ портала + разобранные строки
GET /purchase/<no>               → карточка закупки
GET /purchase/<no>/documents     → список файлов с уже разрешёнными URL
GET /document/<uuid>             → байты файла
GET /health                      → состояние контекста, длина очереди, текущая пауза
```

Что это даёт, помимо опрятности:

- **Ограничитель частоты работает.** Один token bucket на процесс, а не N
  независимых воркеров, каждый из которых «вроде бы вежливый». Портал видит один
  последовательный поток
- **Остальная система тестируется без портала.** Gateway подменяется заглушкой,
  отдающей сохранённые `raw_capture`. Весь конвейер прогоняется на записанном
  трафике, без сети
- **Падение браузера локализовано.** Context умер → gateway поднимает его из
  профиля и повторяет задачу в работе. Воркеры этого не видят, они видят 503 и
  ретраятся
- **Это и есть `PlatformAdapter`** из [05-архитектура.md](05-архитектура.md), но
  ставший границей процесса, а не только интерфейса. Вторая площадка — второй
  gateway с тем же контрактом

Внутреннее устройство gateway:

- одна очередь заданий, конкурентность строго 1
- token bucket: старт **1 запрос в 4 секунды**, подбирается спайком
- **circuit breaker**: серия ошибок подряд → цепь размыкается, пауза удваивается,
  алерт в Telegram; полуоткрытие через N минут одним пробным запросом
- перехват ставится один раз через `context.addInitScript`, а не на каждой странице
- профиль на диске переживает перезапуск процесса

## Решение Q2b. Перехватывать ответы, а не выскребать DOM

Портал — SPA: он сам ходит в своё API по XHR и получает **JSON**. Значит этот
JSON можно взять целиком, вместо того чтобы разбирать отрисованную из него
вёрстку.

```js
context.on('response', async (res) => {
  const url = res.url();
  if (!/\/open-api\/(lots|adverts|files)/.test(url)) return;
  if (res.status() !== 200) return;
  captures.push({
    url, status: res.status(),
    body: await res.text(),
    at: Date.now(),
  });
});
```

Разница принципиальная, а не стилистическая:

| | Разбор DOM | Перехват JSON |
|---|---|---|
| Ломается от | любой правки вёрстки, CSS-классов, порядка колонок | только от смены схемы API |
| Типы | всё строки, суммы и даты парсятся из текста | числа числами, даты датами |
| Полнота | только то, что отрисовано на экране | все поля ответа, включая невидимые в интерфейсе |
| Локализация | зависит от языка интерфейса (портал двуязычный) | не зависит |

Двуязычность здесь особенно важна: в вёрстке казахский и русский варианты идут
вперемешку (видно по любому документу портала), а в JSON это, как правило,
отдельные поля.

Разбор DOM остаётся **резервным путём** на случай, если какой-то экран окажется
отрисован на сервере. Порядок попытки: перехват JSON → разбор DOM → ошибка с
сохранением сырого HTML.

## Решение Q1. Обнаружение нового — два уровня опроса плюс сверка

Push-канала у портала нет, значит «реальное время» — это короткий опрос. Задача:
сделать интервал маленьким, а нагрузку — мизерной.

### Уровень 1 — дозор по вершине, каждые 60 секунд

Один запрос: первая страница списка, сортировка по дате публикации по убыванию,
20 строк.

- верхняя строка известна → **ничего нового, выход.** Один запрос в минуту,
  1440 запросов в сутки — пренебрежимо мало
- верхняя строка незнакома → включается уровень 2

Это стандартный «tip watch»: дешёвая проба, которая почти всегда заканчивается
ничем.

### Уровень 2 — добор, по факту

Идём по страницам вглубь, пока не упрёмся в уже известные строки или не выйдем за
окно курсора. Ограничение сверху — 10 страниц за проход, чтобы одна аномалия не
превратилась в обход всего портала.

### Курсор: водяной знак с перекрытием, а не `>` от последнего

Наивный курсор `published_at > last_seen` теряет записи. Причины прозаические:
одинаковые метки времени у пачки лотов, публикация задним числом, переиндексация
на стороне портала, расхождение часов.

Правильно:

```sql
-- берём с запасом назад
where published_at >= (select last_published_at from harvest_cursor
                       where platform_id = $1 and status = $2) - interval '2 hours'
```

Повторный захват тех же лотов безвреден, потому что вставка идемпотентна:

```sql
insert into lot (platform_id, purchase_external_no, external_no, ...)
values (...)
on conflict (platform_id, purchase_external_no, external_no) do update
   set last_seen_at = now(), ...
returning id, (xmax = 0) as is_new;
```

`xmax = 0` в `returning` отличает вставку от обновления одним запросом — так
сборщик узнаёт, что лот действительно новый, и не ходит в базу второй раз.

**Два разных времени, и путать их нельзя:**

- `published_at` — часы портала. Только для курсора
- `first_seen_at` — наши часы, момент первого захвата. Для сортировки ленты и
  для «сколько прошло с появления»

Лента сортируется по нашему времени. Иначе лот, опубликованный задним числом,
провалится в середину ленты и человек его не увидит — притом что для нас он
новый.

### Уровень 3 — ночная сверка

Раз в сутки в тихий час: проход по окну «последние 72 часа» по `published_at`
целиком, игнорируя курсор. Ловит всё, что проскочило мимо дозора — простой
сервиса, аномалии сортировки, ошибки на стороне портала. Находки здесь
логируются отдельно: их количество прямо показывает, насколько можно доверять
дозору.

## Решение Q2c. Что такое «вся информация»

Три источника с разной ценой, разной формой и разной изменчивостью. Смешивать их
в один запрос нельзя — у них разная частота обновления.

| Источник | Цена | Что даёт | Когда берём |
|---|---|---|---|
| **Строка списка** | 1/20 запроса | номер закупки и лота, предмет, плановая сумма без НДС, заказчик, место, срок, статус | при каждом обходе |
| **Карточка закупки** `#/ext(popup:item/<no>/advert)` | 1 запрос на закупку | цена за единицу, окна приёма, контакты, перечень файлов | один раз при появлении, затем при изменении |
| **Файлы** | 1 запрос на файл | собственно документация | один раз на sha256 — никогда повторно |

Строки списка достаточно, чтобы лот **попал в ленту и сработали подписки** —
L0-признаки (категория, ценовой сегмент, регион, срок) все в ней. Это и есть
такт 1 уведомления: секунды с момента появления, до скачивания документов.

## Решение Q3. Хранение: сырое → нормализованное → производное

### Главное правило: сначала сохранить, потом разбирать

**Сырой ответ портала пишется в базу дословно, до любого парсинга.** Разбор —
чистая функция `raw → normalized`, версионированная и перезапускаемая.

Смысл в одной фразе: когда портал изменит формат (а он изменит), мы
перезапускаем парсер по сохранённому сырью, вместо того чтобы навсегда потерять
данные, собранные до поломки. Стоит это дёшево — JSON на фоне PDF не весит
ничего и отлично жмётся.

```sql
create table raw_capture (
  id            bigserial,
  platform_id   int  not null,
  kind          text not null,   -- list | advert | doc_index
  external_key  text not null,   -- номер закупки, либо 'list:published:p1'
  fetched_at    timestamptz not null default now(),
  http_status   int,
  payload       jsonb not null,
  payload_sha   bytea not null,
  parser_ver    text,
  primary key (id, fetched_at)
) partition by range (fetched_at);
```

Секции по месяцам, старые — под `pg_dump` в холодное хранилище. `lot_snapshot` из
[04-данные.md](04-данные.md) ссылается на `raw_capture.id`, а не дублирует payload.

### Content hash считается по нормализованным полям, а не по сырым байтам

Тонкий, но важный момент. В сыром ответе меняются метки времени, счётчики,
служебные идентификаторы — хеш по нему отличается при каждом запросе, и любой
лот выглядел бы изменившимся постоянно.

Хеш берётся по каноническому JSON из полей, изменение которых нас реально
интересует:

```js
const watched = {
  subject, amount_no_vat, status,
  bids_open_at, bids_close_at,
  doc_count, doc_hashes: docs.map(d => d.sha256).sort(),
};
const contentHash = sha256(canonicalJson(watched));
```

Изменился хеш → пишем `lot_change`, определяем вид изменения и решаем, нужен ли
переразбор. Не изменился → трогаем только `last_seen_at`, и ни одна задача в
очередь не уходит.

### Файлы — адресуемое содержимым хранилище

Путь выводится из хеша, а не из имени файла:

```
storage/ab/cd/abcdef0123…4567.pdf
```

Что это решает бесплатно: нет коллизий имён (`Приложение №1.pdf` встречается в
каждой второй закупке), нет проблем с кириллицей и пробелами в путях, дедупликация
получается сама, переезд на S3 — смена префикса. Человекочитаемое имя живёт в
`document.filename` и в `document_link`, к пути отношения не имеет.

Экономия здесь не теоретическая: типовая тендерная документация одного заказчика
повторяется от закупки к закупке, и совпадение по sha256 означает, что файл
**не скачивается и не разбирается заново** — переиспользуется готовый разбор
(`analysis.reused_from_id`, `cost = 0`).

### Что в колонках, что в jsonb

Правило простое: **в колонках — то, по чему фильтруют и сортируют** (фасеты
ленты: категория, ценовой сегмент, лицензия, регион, сроки). Всё остальное — в
`jsonb` рядом. Колонка с индексом стоит дорого только при записи, а записей здесь
мало; но каждая лишняя колонка — это миграция при каждом изменении портала.

## Решение Q4. Передача обработчику

### Транзакционный outbox: не делать двойную запись

Классическая ошибка — записать лот в базу, а потом отправить задачу в очередь.
Между этими двумя действиями процесс может умереть, и получится либо лот без
задачи (молча не разобран), либо задача без лота (вечные ретраи).

pg-boss живёт в том же Postgres, поэтому лечится бесплатно — **одной
транзакцией**:

```js
await db.tx(async (t) => {
  const { id, isNew } = await upsertLot(t, lot);
  await saveRawCapture(t, raw);

  if (isNew || contentChanged) {
    await boss.send('docs.fetch', { lotId: id }, {
      db: t,                                       // та же транзакция
      singletonKey: `docs:${id}:${contentHash}`,   // ключ идемпотентности
      retryLimit: 5,
      retryBackoff: true,
    });
  }
});
```

Коммит либо прошёл целиком, либо не прошёл вовсе. Потерянных задач не бывает
по построению.

### Идемпотентность обязательна везде

Очередь даёт **at-least-once**, и окно перекрытия в курсоре гарантирует, что одни
и те же лоты будут встречены повторно. Значит повтор обязан быть безвредным:

| Что | Ключ идемпотентности |
|---|---|
| Лот | `(platform_id, purchase_external_no, external_no)` |
| Задача | `singletonKey` с `content_hash` внутри |
| Документ | `sha256` |
| Разбор | `(lot_id, level, prompt_version, input_hash)` |

Последняя строка — про деньги: без неё падение воркера в середине анализа
приводит к повторной оплате того же вызова модели.

### Очередь на этап, а не один общий воркер

У этапов разные узкие места, поэтому и настройки разные:

| Очередь | Конкурентность | Чем ограничена | Ретраи |
|---|---|---|---|
| `harvest.tip` | 1, крон 60 с | gateway | 3, backoff |
| `harvest.detail` | 1 | gateway | 5, backoff |
| `docs.fetch` | 1 | gateway | 3, затем флаг `documents_incomplete` |
| `text.extract` | = числу ядер | CPU, OCR | 2 |
| `fragment.parse` | = числу ядер | CPU | 1 |
| `analyze.l1` | 4–8 | лимиты Claude API | 5, backoff на 429 и 529 |

### Противодавление: сборщик не останавливается никогда

Если очередь `analyze.l1` разрослась, обход и скачивание **продолжаются**, а
постановка задач на анализ придерживается.

Причина асимметрии: анализ можно наверстать в любой момент — документы уже лежат
на диске. А обход наверстать нельзя: курсор привязан ко времени, и лот, не
замеченный вовремя, может оказаться уже недоступным или потерять смысл, потому
что срок подачи прошёл. Лента при этом остаётся живой — L0-признаки есть сразу,
уведомления такта 1 уходят.

## Решение Q5. Наблюдаемость сборщика

### Алерт на отсутствие, а не на ошибку

Самый опасный отказ — тихий. Сломанный парсер молча отдаёт ноль строк, и система
неотличима от «новых лотов нет».

```sql
-- каждые 30 минут
select max(first_seen_at) from lot;
-- старше 3 часов в рабочее время → алерт в Telegram
```

То же для gateway: не было ни одного успешного обхода за N часов → алерт.

### Контроль качества разбора

Скользящее окно по последним 200 строкам, доля успешно распознанных полей:

```
amount_no_vat распарсился в 99.5 % строк
bids_close_at распарсился в 98.1 % строк
```

Падение ниже 95 % по любому обязательному полю означает, что портал сменил формат.
Реакция: алерт, **обход продолжается**, сырьё продолжает писаться, постановка на
анализ ставится на паузу. Собирать сырьё во время поломки важнее, чем разбирать:
разобрать можно потом, собрать заново — нельзя.

### Метрики, которые стоит писать с первого дня

- задержка обнаружения: `first_seen_at − published_at`, персентили
- запросов к порталу в час, текущая пауза, состояние circuit breaker
- находки ночной сверки — сколько лотов дозор пропустил
- доля попаданий дедупликации по sha256 — прямо показывает экономию

## Бюджет задержки

Что реально означает «в реальном времени»:

| Шаг | Время |
|---|---|
| Дозор заметил | p50 30 с, p95 60 с |
| Карточка закупки | ~3 с |
| **Лот в ленте с L0-признаками, такт 1 уведомления** | **≈ 1 минута** |
| Документы (5 файлов при паузе 4 с) | ~20 с |
| Извлечение текста и фрагментов | ~30 с |
| Разбор L1 | ~40 с |
| **Такт 2 — выжимка** | **≈ 3 минуты** |

Минута до появления в ленте упирается в интервал дозора, а не в портал. Хотим
быстрее — уменьшаем интервал, платим запросами. Три минуты до выжимки упираются в
скачивание и модель, и это уже предел разумного.

## Что из этого зависит от спайка Ш-0

Честное разделение — что устоит при любом исходе, а что придётся переделать.

**Устоит в любом случае:**

- Portal Gateway как отдельный процесс с узким контрактом
- «сначала сохранить сырое, потом разбирать»
- адресуемое содержимым хранилище файлов
- транзакционный outbox и идемпотентность
- алерт на отсутствие и контроль качества разбора

**Зависит от результатов спайка:**

| Решение | Что его сломает | Запасной вариант |
|---|---|---|
| Перехват JSON | экран отрисован на сервере | разбор DOM, тот же интерфейс gateway |
